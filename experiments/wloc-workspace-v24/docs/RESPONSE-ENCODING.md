# 定位响应的编码头修复

## 已复现的代码缺陷

原始固定脚本及 v2.3 在最后输出响应时，无论正文是否被改写，都会把 `Content-Encoding: gzip` 改为 `identity`。但未设置目标、gzip 解压失败或无法解析定位响应时，前面的处理器仍返回原始正文。如果原正文保持 gzip，这个标头就与实际字节不一致，客户端可能无法正常解码。

这是脚本层可复现的缺陷，不代表已确认任何具体手机故障的原因。TLS 握手失败发生在响应脚本之前，本修复不能解决该层问题。

## 修复后的行为

- 未设置目标、没有正文或解析失败：保留原正文、编码和状态。Shadowrocket 与 Stash 的普通透传头保持不变。
- 原响应不被分步改写。先构造新的正文、响应和 headers；构造失败时仍返回未变动的原响应，避免留下“gzip 头配明文正文”的半成品。
- 只有完成实际正文改写后：按不区分大小写移除 Content-Encoding、Transfer-Encoding 和旧 Content-Length，设置唯一正确的 Content-Length。
- 保留 Quantumult X 的既有输出适配，包括其长度/传输头清理和 bodyBytes 转换；不在最终输出时把保留的 gzip 改成 identity。

定位字段解析与随机偏移算法没有改变。正式存储键、首次备份和失败写入行为不受此修复影响。

## 可重复构建

原仓库只提供打包后的定位响应脚本。`vendor/wloc-007ef075.js` 固定于 JarynXu/wloc 的 `007ef07550ea0e4706a14739d033a6a8e814e171`，SHA256 为 `a1b361e60f0b434585260fb59c65d1ddbe3bff89ace3639f592e7d8af432b3c1`。

`build-responder.mjs` 先核对该哈希，再应用三个必须恰好匹配一次的补丁：保留先前的经纬度 0 值修正；成功改写后的编码头处理；移除最终无条件 identity 改写。构建不下载新源，也不会静默接受变化的上游 bundle。

## 验证

39 项定向测试覆盖三种宿主输出、头名大小写、三种正文载体、无目标透传、空响应、损坏 gzip、解压后无法解析、成功压缩/非压缩改写、只读响应/头与提交阶段异常，以及真实 loopback HTTP/fetch 解码。最初 22 项在旧候选上有 17 项失败，补丁后全部通过；随后补充了真实 HTTP 回归、三宿主成功矩阵和只读响应对象测试。完整候选共 263 项测试通过。

这些测试只使用合成 protobuf 和本地存储，不是 iOS / Shadowrocket 真机验证，也不证明 Apple 地图恢复定位。
